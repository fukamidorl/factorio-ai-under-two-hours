## 理解任务

| 用户的说法 | 对应的操作 |
| --- | --- |
| “同一个种子和路线”“从零开始” | 在《异星工厂》2.1.25 基础游戏中，根据 `world/map-gen-settings.json` 生成创建角色前的新地图。固定种子、地图生成设置和施工坐标。运行要求以 `manifest.json` 为准。 |
| “让我看到游戏画面” | 选用 `visible`。开场显示角色视角，随后通过游戏内镜头展示采矿、发电、研究和火箭发射井。运行中保持窗口可见，完成时保留胜利画面。 |
| “两小时以内” | 使用游戏内时间。用于判定的事件须发生在地图开始后的第 `432000` 刻之前。`*_elapsed` 从自动操作开始计时，`*_world_time` 还计入开场。需要现实时长时单独计量。 |
| “卡住就修” | 先诊断当前试跑。若要测试修正，请保留基准和候选试跑，结合日志核实改动及结果。 |
| “获得成就” | 在基础游戏的常规游玩中检查成就条件。这里记录的是 Lua 辅助施工和供料的试跑结果。 |

以用户最新的明确要求为先。用[清单](../../manifest.json)核对执行条件，用[启动器](../../run_route.py)和 [Lua 模组](../../mod/first-rocket-route-check_0.1.0/)核对实际行为，用[验证记录](../../reference/package_verification.json)核对实测结果。不同译本说法有出入时，核查实现和实测记录。开发时间线中的旧存档和时刻用于说明当时的实验。

从用户的要求判断是复现还是改进、是否显示窗口，以及要确认发射还是跟进至到货。复现时先用打包版路线。改进时先定位受影响的工序，确定用来对照的基准，再编辑代码。

## 启动与监控

请在仓库根目录执行。以下是首次试跑示例。每次选用新的运行名称，并保留 `runs/<名称>/` 中供比较的原有结果。

~~~powershell
py -3 -X utf8 .\run_route.py check
py -3 -X utf8 .\run_route.py visible watch-01
py -3 -X utf8 .\run_route.py report watch-01
~~~

如需用日志核实全程，可执行 `headless verify-01`。带画面模式返回 `launched` 表示已提交启动请求。若启动由 Steam 接手，先检查其自定义参数对话框和 `factorio-current.log`，再用 `opening-start.json` 和 `report` 核实游戏已推进。无界面模式会等待《异星工厂》的测试模式运行结束。

启动器将专用模组放入本次运行的独立可写目录。用屏幕操作检查 Steam 提示或游戏画面时，仍以启动器和日志作为执行与进度的依据。早期 MCP 连接与单块铁板测试所用的工具见下文。 [游戏运行方法与所用工具](METHOD_AND_TOOLS.md)

## 判定结果

- **带画面。** 确认依次记录 `satellite-loaded`、`launch` 和 `victory`。`goal-met` 要求 `victory_world_tick < 432000`。胜利窗口打开时的快照可能早于物流接驳站到货及发射统计更新。
- **无界面。** 确认依次记录 `satellite-loaded`、`launch` 和 `delivery`，时间条件为 `launch_world_tick < 432000`。完成时检查启动器退出码为 0，状态为 `goal-met`，`space_science` 为 1,000。测试模式依据实际的发射、到货事件和数量判定。
- `time-missed` 表示已完成该模式的流程，但超过目标时间。`starting`、`opening` 和 `running` 是进度状态。遇到 `failed` 时查看 `error` 及对应日志。报告通关时间时附上完成证据。

打包版无界面验证中，发射为自动操作开始后的第 `397078` 刻，到货为第 `397647` 刻，发射对应的地图刻为 `398432`。此前的带画面完整试跑在第 `406737` 刻发射、第 `406738` 刻胜利。打包版的带画面复查范围为开场至蒸汽发电后的镜头切换。 [打包版事件](../../reference/package_verification.json) · [此前的事件](../../reference/confirmed_runs.json)

## 排查问题

每次试跑写入 `runs/<名称>/`，模组输出在其中的 `script-output/`。先找出最早停止推进的阶段和观测到的事件刻。

| 症状 | 证据与排查步骤 |
| --- | --- |
| `check` 检测到版本或校验值不符 | 核对 `--factorio` 指定的路径和程序的 `--version`。输入与清单不一致时重新获取发布文件。若问题只出现在 Windows 的 Git 检出后，检查 `.gitattributes` 和换行符转换。改动输入后的测试请单独记录。 |
| 启动时没有进展 | 查看 `world-generation.log` 确认地图生成，再用 `run.log` 和 `factorio-current.log` 确认存档是否读入。带画面运行还要检查 Steam 的自定义参数确认框以及游戏是否暂停。 |
| 开场采矿或蒸汽发电停滞 | 查看 `opening-error.json` 和 `supply-trial.json` 中的当前任务。检查施工坐标、初始物品、煤和水、已经接通的进水口，以及电线杆是否与坠船残骸冲突。 |
| 研究停滞 | 对照 `through-latest.json` 和 `through-stream.jsonl`。查看 `research`、`active_labs`、`progress` 和各色科技包产量与消耗量，再对照 `steam_mw`、`steam_capacity_mw` 和设备 `status`，定位最先短缺的科技包或电力环节。 |
| 设备不少但产量偏低 | 查看 `warehouse`、`launch_reserve`、设备状态和分时段产量。沿矿石运出、燃料、电力、供水、进料与出料逐段查验，区分安装数量与实际运转。 |
| 紫瓶、黄瓶和发射原料互相争抢 | 跟踪紫瓶所需的石矿、石砖、铁轨、插件和电炉。对照黄瓶和火箭共用的处理器与轻质框架，检查炼油的三种产物、裂解、用水和塑料供应。调整配给前先核对剩余研究量和发射预留量。 |
| 发射井无法放置或发射较慢 | 查坠船残骸、电力连接、`blocked_sites`、可转用的组装机，以及发射井、研究、火箭的预留材料。检查发射井是否装有 4 个速度插件 3，并定位装载、发射和到货中最后确认的事件。 |
| 只有镜头画面停止更新 | 将 `watch-error.txt`、`watch-latest.json` 和生产日志对照，分别检查游戏画面和工厂进度。 |

`through-stream.jsonl` 包含每分钟的快照和里程碑事件。判断停滞时应比较多次更新。为验证修正，使用相同的地图生成设置，比较受影响时段的产量、库存和电力，再通跑至发射及到货，并记录对后续工序的影响。

查代码时，`opening.lua` 负责开场采矿到初期蒸汽发电，`design.lua` 保存布局和研究顺序，`factory.lua` 负责施工、生产、调配与发射，`watch.lua` 负责显示和镜头。`control.lua` 将这些模块接到起动条件与游戏事件上。

交接时请写明运行模式、游戏版本、种子、运行名称或代码版本、最后测得的事件刻、最早的异常、具体证据字段或日志、试过的修改以及是否通过全程验证。公开共享前，从日志中提取复现所需的部分。
