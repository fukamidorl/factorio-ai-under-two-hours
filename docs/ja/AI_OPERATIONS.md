## 依頼をどう読むか

| 依頼の表現 | このプロジェクトで開始するときの意味 |
| --- | --- |
| 「同じシードと手順」「一から」 | Factorio 2.1.25の基本ゲームで、`world/map-gen-settings.json` からプレイヤー作成前の新規マップを生成する。シードに加えて鉱床・水域の設定と設備座標を固定する。`manifest.json` が実行条件。 |
| 「画面を見せて」 | `visible` を選ぶ。初動はキャラクター、その後は採掘・発電・研究・サイロをゲーム内カメラで映す。進行中はウィンドウの表示を保ち、勝利画面が出たところで表示を残す。 |
| 「2時間切り」 | 目標はゲーム内2時間。マップ開始からの判定ティックは `432000` 未満。`*_elapsed` は自動操作開始から、`*_world_time` は初期演出を含む。現実の経過時間が必要なら別に計測する。 |
| 「詰まったら直す」 | まず現在の試走を診断する。修正を試す依頼なら比較元と新しい試走を分け、変更した点と結果をログで確認する。 |
| 「実績を狙う」 | 実績の確認は基本ゲームの通常プレイとして扱う。この資料のタイムは施工や配給にLuaを使う自動運転の結果。 |

利用者の最新の依頼を確かめ、実行条件は [manifest.json](../../manifest.json)、実装は [ランチャー](../../run_route.py) と [Lua MOD](../../mod/first-rocket-route-check_0.1.0/)、計測済みの結果は [検証記録](../../reference/package_verification.json) で読む。異なる言語版の説明が食い違う場合も、バージョン、座標、判定式、数値はこの実装と記録で照合する。過去の時系列に出るセーブと時計は、その時点の実験を説明する材料。

再現か改良か、画面の有無、発射・着荷のどこまで確認するかを依頼から決める。再現の依頼ではまず配布済みの工程を使う。改良の依頼では、症状を起こした工程と比較に使う基準を特定してから編集する。

## 起動と監視

リポジトリのルートで実行する。例の試走名は初回用。実行ごとに新しい名前を使い、比較元の `runs/<名前>/` を参照できる状態にする。

~~~powershell
py -3 -X utf8 .\run_route.py check
py -3 -X utf8 .\run_route.py visible watch-01
py -3 -X utf8 .\run_route.py report watch-01
~~~

数値の通し検証では `headless verify-01` を実行する。`visible` の `launched` は起動を要求した段階。Steamが起動を引き継いだ場合は個別の起動確認と `factorio-current.log` を見てから、`opening-start.json` および `report` でゲームが進んでいることを確認する。`headless` はFactorioのテストモードで進行し、最後の結果まで待つ。

ランチャーが専用MODを試走ごとの書き込み先に配置する。観戦時のSteam確認やゲーム画面の確認に画面操作を使う場合も、実行と進捗確認はこのランチャーとログを起点にする。初期のMCP接続・鉄板試験のツールの使い分けは以下を参照。 [Factorioの扱い方と使用ツール](METHOD_AND_TOOLS.md)

## 成功の読み方

- **画面あり**では `satellite-loaded`、`launch`、`victory` の順で記録され、`victory_world_tick < 432000` なら `goal-met`。勝利画面を表示した状態では、着荷や発射統計が更新される前のスナップショットを読む場合がある。
- **画面なし**では `satellite-loaded`、`launch`、`delivery` の順で記録され、`launch_world_tick < 432000` なら時間条件を満たす。完了時にランチャーの終了コード0と `goal-met`、`space_science` が1,000であることを確認する。テストモードの確認は発射・着荷イベントと実数に基づく。
- `time-missed` はモードの完了を確認した上での時間超過。`starting`、`opening`、`running` は途中経過。`failed` は `error` と該当ログを読む。完走タイムは完了を示すログを添えて報告する。

基準は画面なしの発射 `397078`、着荷 `397647` ティック。いずれも操作開始からの値。マップ開始からの発射は `398432` ティック。先行の画面付き試走は発射 `406737`、勝利 `406738` ティックで、配布版の画面付き再検証の範囲は蒸気発電後のカメラ切り替えまで。 [配布版のイベント](../../reference/package_verification.json) · [先行試走のイベント](../../reference/confirmed_runs.json)

## 問題の切り分け

標準の出力先は `runs/<名前>/`、MODの出力はその中の `script-output/`。まず時刻と最初に変化が止まった工程を探す。

| 症状 | 読むものと対処 |
| --- | --- |
| `check` が版・ハッシュで失敗 | `factorio.exe --version` と `--factorio` の指定先を照合。入力差なら配布物を取り直す。WindowsでGit経由の取得後だけ起こる場合は `.gitattributes` と改行変換を確認する。変更した入力で試す場合は別の比較として記録する。 |
| 開始時に進まない | `world-generation.log` でマップ生成を確認し、`run.log` と `factorio-current.log` でゲームの読み込みを確認する。画面付きの場合はSteamのカスタム引数確認やゲーム内の一時停止も見る。 |
| 序盤の採掘・蒸気が止まる | `opening-error.json` と `supply-trial.json` の現在作業を確認。設置位置、初期所持品、石炭と水、稼働済みの給水口、電柱・墜落船との衝突を調べる。 |
| 研究が止まる | `through-latest.json` と `through-stream.jsonl` を比較する。`research`、`active_labs`、`progress`、各色の生産・消費を調べ、`steam_mw` と `steam_capacity_mw`、稼働設備の `status` を照合する。最初に足りなくなったパックや電源を特定する。 |
| 機械は多いのに資材が出ない | `warehouse` と `launch_reserve`、設備状態、区間当たりの生産を見る。鉱石の搬出、燃料・電気・水、給材と搬出の順で確認し、設備の配置数と実稼働を見分ける。 |
| 紫、黄、発射用資材が競合 | 紫の原石・レンガ・レール、モジュール・電気炉を確認。黄と発射で取り合う制御基板・軽量化素材、精油3出力と分解、水、プラスチックを追う。研究の残量とサイロの予約在庫を照合して配給を変更する。 |
| サイロが置けない、発射が遅い | 墜落船、電柱接続、`blocked_sites`、組立機の転用、サイロ本体と研究・発射材料の取り置きを確認する。速度モジュール3が4個揃ったか、積み込み・発射・着荷のどこまで進んだかを読む。 |
| カメラの表示だけ止まる | `watch-error.txt`、`watch-latest.json` と生産ログを照合する。ゲーム画面の復旧と、工場自体の状態確認をそれぞれ進める。 |

`through-stream.jsonl` は1分ごとのスナップショットと工程イベントを含む。活動の有無は複数の更新を見て判断する。変更時は、同じマップ生成条件でまず該当区間の流量・在庫・電力を比べ、改善したら発射・着荷までの通しで検証する。先の工程で生じる副作用も記録する。

コードを追うときは `opening.lua` が採掘から初期蒸気まで、`design.lua` が配置と研究順、`factory.lua` が施工・生産・配給・発射、`watch.lua` が表示とカメラを担当する。`control.lua` でそれらの起動条件とイベントを確認できる。

引継ぎには実行モード、ゲーム版・シード、試走名かコードの版、最後の実測ティック、最初の異常、その根拠の項目とログ、試した変更、通し検証の有無を書く。外部に共有するログには、再現に必要な部分を抽出する。
